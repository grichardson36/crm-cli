# Mesh network architectures (Reticulum, Meshtastic, MeshCore) and what they mean for the sync contract

**Owner decision 2026-10-26: IP only, no radio, no encryption layer.** Peer devices are the owner's own and trusted, and no data passes through untrusted devices. The compact binary record, sealed bundles, chunking, schema dictionary and constrained profile (I1 to I3, I8, I11) are dropped. Kept: the relay as a role in our own contract, change ids for duplicate suppression, and a per-device version vector as the cursor (I7). Transport stays JSON over HTTP on Tailscale or LAN.

Date 2026-10-26. Trigger: the owner wants relay-assisted peer devices (any device can be a relay, for example an always-on Raspberry Pi) and wants to emulate the network architecture of Reticulum (with LXMF), Meshtastic and MeshCore. Feeds [[sync-safe-data]]. Builds on [[research-sync-standardization]] (Y-numbers, Part "Smallest real contract" and B-numbers) and [[research-sync-engines]] (E13 op-log with HLC). Not repeated here: engine-by-engine fit for Go + SQLite.

Evidence tags: doc (first-party page read on 2026-10-26 through a summarizing fetch, so re-read exact numbers and field names before they go in a spec), search (search summary or third-party page only), gap (not verified). Every fetched page passed through a summarizing model. See "Could not verify".

## Findings

### Reticulum and LXMF

- M1. **Roles.** An "Instance" is the default. Any instance becomes a Transport Node with `enable_transport = Yes` (default No). Transport Nodes forward packets, propagate announces, keep path tables, answer path requests and cache public keys. The manual says stable, always-on, well-connected nodes are the best candidates, that making every node a transport node usually degrades performance and reliability, and that a network should have "enough" transport nodes and not many more (doc). A Pi on mains power fits this role directly. https://markqvist.github.io/Reticulum/manual/networks.html
- M2. **Routing model is path-based, with hop-by-hop state.** No node knows the full path. Each transport node knows only the next hop for a destination hash. Paths are learned from announces and from 51-byte path requests that transport nodes answer (doc). Interface modes (`full`, `gateway`, `access_point`, `roaming`, `boundary`) change how announces cross between interfaces. The page lists them without behavior detail (gap on what each does). https://markqvist.github.io/Reticulum/manual/understanding.html
- M3. **Identity and addressing.** An Identity is 512 bits: a 256-bit X25519 encryption key plus a 256-bit Ed25519 signing key (doc, `Identity.KEYSIZE = 512`). Addresses are destination hashes: 128 bits (16 bytes), truncated SHA-256 (doc, `TRUNCATED_HASHLENGTH = 128`). A destination hash derives from the app name plus aspects plus the identity's public key, so the same name under two identities gives different addresses. Destination types: Single, Plain, Group (pre-shared AES-256 key), Link. Plain destinations are unencrypted and cannot be routed over multiple hops (doc). https://markqvist.github.io/Reticulum/manual/reference.html
- M4. **Encryption, and what relays see.** Primitives: Ed25519, X25519, HKDF, Fernet-style tokens (AES-256-CBC, HMAC-SHA256), SHA-256/512 (doc). Single packets use a fresh ephemeral key per packet, optional per-destination ratchets add forward secrecy. Links give forward secrecy via X25519. A transport node sees the header (destination hash, hop count, context) but not the payload. Packet proofs are Ed25519 signatures over the packet hash. Interface Access Codes (IFAC, 1 to 64 bytes) can authenticate an interface so only holders of a shared secret can join that segment (doc). https://markqvist.github.io/Reticulum/manual/understanding.html
- M5. **Packet sizes and bandwidth assumptions.** Physical MTU 500 bytes. Header 2 bytes, addresses 16 or 32 bytes, context 1 byte, data 0 to 465 bytes. `Packet.ENCRYPTED_MDU` = 383 bytes. Minimum usable throughput 5 bits per second, half duplex. Announce = 167 bytes on the wire. Link setup = 3 packets, 297 bytes total. Link keepalive about 0.45 bits per second per link (doc). Announce bandwidth is capped at 2% of each interface by default, configurable (doc). Reference radio is an RNode LoRa device (433/868/915 MHz) but any medium works: serial, Ethernet, WiFi, TCP/UDP tunnels (doc).
- M6. **Announces and discovery.** An announce is signed (Ed25519) and carries destination hash, public key, optional app data and a random blob. Default propagation limit is 128 hops, retransmit count 1. Duplicates are ignored. Queued announces are prioritised by hop count (closer first), so local connectivity works before global convergence. Doc claim: full convergence takes about a minute even at 128 hops (doc, claim not tested). There is no address planning. Release 1.5.x adds interface discovery with auto-connect (doc, RNS 1.5.5 dated 2026-09-29, https://github.com/markqvist/Reticulum/releases ). Network Identities let a node check that a discovered interface belongs to a trusted operator.
- M7. **Duplicates and loops.** The manual describes duplicate-announce suppression and link-table tracking (unproven link entries time out). It does not describe loop handling for ordinary data packets (gap). Path state is per next hop with hop counts, and the 128-hop cap bounds announce loops.
- M8. **Application data transport inside Reticulum.** Three layers exist and all need an established Link (doc, examples page https://markqvist.github.io/Reticulum/manual/examples.html ):
  - Resource: arbitrary-size transfer over a link with auto-compression (default on), splitting, sequencing, integrity check, reassembly, automatic retransmission, progress callbacks. Size limits and the hashmap mechanism were not on the pages read (gap). RNS 1.5.1 notes mention a `MAX_EFFICIENT_SIZE` constant for stream-based sources (value not found).
  - Channel: reliable, ordered typed messages over a link. A message subclass has a 2-byte `MSGTYPE` (0xf000 and up reserved), `pack`/`unpack`, and must fit in one packet (`Channel.MDU`, slightly below the link MDU). `is_ready_to_send()` gives back-pressure. Window mechanics were not stated (gap).
  - Buffer: a stream (file-descriptor-like, `stream_id`) layered on a Channel with `read/write/flush/close`.
  - The manual's example warns that compression, encryption and hashmap sequencing are slow on weak CPUs and may cause timeouts, and recommends the Bundle class for big files (doc).
- M9. **LXMF (Lightweight Extensible Message Format) message.** Wire fields: destination (16 B), source (16 B), Ed25519 signature (64 B), payload (msgpack list: timestamp as float, content, title, optional fields dict). Total overhead 111 bytes. The message-id is SHA-256 over destination, source and payload and is not stored in the message. The signature covers destination, source, payload and message-id (doc). Delivery methods: opportunistic (one packet, per-packet key), direct over a Link (forward-secret, AES-128 per LXMF page; Reticulum page says AES-256 tokens, a discrepancy to check), and via a propagation node. `fields` is an extensible dictionary, and the README suggests it can carry email-like attachments but defines no attachment API (doc). LXMF 1.2.0 (30 September, year not shown) improves delivery over extremely low-bandwidth links and adds version signalling to propagation node announces (doc, https://github.com/markqvist/LXMF/releases ). https://github.com/markqvist/LXMF
- M10. **Propagation nodes (store-and-forward).** `lxmd -p` runs one. A sender hands the encrypted message to a propagation node when the recipient is offline, and the recipient later fetches from any node. Nodes peer with each other and sync automatically, forming a distributed encrypted store (doc). Since LXMF 0.9.0 (2 November, year not shown): clients compute a proof-of-work "propagation stamp" per message, nodes verify it cheaply, operators set stamp cost and peering cost individually, peering keys are validated, sync requests are throttled, message size and per-sync size have separate limits, and peers outside the auto-peering range are dropped. Pre-0.9.0 nodes cannot sync with newer ones (doc). The propagation dedup key is `transient_id = SHA-256(lxmf_data)` (search, a JS port's docs, https://reticulum.js.org/classes/_reticulum_core.LXMRouter.html ). Numeric default limits and stamp costs were not found (gap). The relay holds only ciphertext addressed to a destination hash. It can see the destination hash, size and arrival time (inferred from the design, not stated).
- M11. **Operator UX.** One config file with interface sections. `rnstatus`, `rnpath` and similar utilities exist (recollection, not verified today). A person enables transport and picks interfaces. Peering between propagation nodes is automatic within cost limits. No address planning (doc).

### Meshtastic

- M12. **Roles (device config).** CLIENT (rebroadcasts only when nobody else has), CLIENT_MUTE (never forwards others), CLIENT_HIDDEN, CLIENT_BASE (always rebroadcasts for favourited nodes), ROUTER (always rebroadcasts once, visible in topology), ROUTER_LATE (rebroadcasts once after all others), REPEATER (always rebroadcasts once, hidden from node list), TRACKER, SENSOR, TAK, LOST_AND_FOUND. Rebroadcast modes: ALL (default), ALL_SKIP_DECODING (REPEATER only), LOCAL_ONLY, KNOWN_ONLY, NONE, CORE_PORTNUMS_ONLY (doc). ROUTER warns of high power use and automatic ESP32 power saving. ROUTER_CLIENT was deprecated in firmware 2.3.15 (doc). https://meshtastic.org/docs/configuration/radio/device/
- M13. **Routing model is managed flooding, plus next-hop routing for direct messages since 2.6.** A node overhears and cancels its own rebroadcast if another node already sent the packet. Contention window depends on SNR, so distant (low SNR) nodes tend to go first. Each rebroadcast decrements a 3-bit HopLimit, `HopStart` keeps the original. Default hop limit 3, maximum 7 (doc, https://meshtastic.org/docs/configuration/radio/lora/ ). Direct messages begin as floods. A node that relayed the original and sees the reply becomes the learned next hop (1-byte `next_hop` field), others stay silent, and the last retry falls back to flooding (doc, https://meshtastic.org/docs/overview/mesh-algo/ ).
- M14. **Identity and addressing.** A 32-bit node number `from`/`to`, with 0xFFFFFFFF meaning broadcast to a channel. Since the PKC feature, each node has an X25519 key pair and nodes trust the first public key they hear for a node number (trust on first use, doc). `relay_node` and `next_hop` carry only the last byte of a node number (doc, mesh.proto https://raw.githubusercontent.com/meshtastic/protobufs/master/meshtastic/mesh.proto ).
- M15. **Encryption and what relays see.** Channel messages: per-channel pre-shared key, AES-128 or AES-256 in CTR mode. The default channel key `AQ==` is public. Anyone with the key reads everything and "can send unsigned packets claiming to be any node". Firmware 2.8.1+ can use AES-CCM with a 12-byte tag (all nodes on the channel must match). Direct and admin messages: X25519 shared key, AES-256-CCM. No forward secrecy. The packet header is never encrypted: destination, sender, packet id, flags, channel hash, next hop and relay node are visible to every relay, and relays do not need the key to forward (doc, https://meshtastic.org/docs/overview/encryption/ ). So Meshtastic relays can carry traffic they cannot read, but a relay learns who talks to whom.
- M16. **Packet size and bandwidth.** `DATA_PAYLOAD_LEN = 233` bytes inside the Data protobuf, and a 16-byte header outside it (doc, mesh.proto). Preset raw data rates (theoretical, excluding headers, hops and retransmits): Long Fast 1.07 kbps (default in some regions), Long Moderate 0.34 kbps, Medium Fast 3.52 kbps, Short Fast 10.94 kbps, Short Turbo 21.88 kbps (doc, https://meshtastic.org/docs/overview/radio-settings/ ). Duty cycle 10% in EU_433/EU_868 and 2.5% (10% for ROUTER roles) in EU_866 (doc, LoRa config page).
- M17. **Duplicates and loops.** Suppression works by overhearing another rebroadcast. Packet `id` is a per-sender 32-bit value "used for acknowledgments and flooding" (doc). The docs do not describe the duplicate cache size or window (gap). Loops are bounded by the hop limit.
- M18. **Reliability.** Reliable broadcasts: sender treats an overheard rebroadcast as an implicit ACK, at most 3 sends. Reliable direct messages: real ACK, at most 5 sends (doc, mesh-algo).
- M19. **Store-and-forward and application data hooks.**
  - Store & Forward module: a PSRAM-equipped ESP32 set to ROUTER or `is_server` (2.4+) stores packets and replays history on request. Default records 0 = two-thirds of PSRAM, about 11,000 records. Heartbeat every 15 minutes. Clients on app versions 2.2.23+ request history, on Android by sending the direct message text "SF" (doc/search, https://meshtastic.org/docs/configuration/module/store-and-forward-module/ ). A third-party page says 240 minute window and 25 messages returned (search, https://d-central.tech/meshtastic-store-forward/ , conflicts with official figures, unverified). The portnum `STORE_FORWARD_APP` (65) is marked "Work in Progress" in the proto and `STORE_FORWARD_PLUSPLUS_APP` (35) exists with no description in what I read (doc, portnums.proto).
  - Application data: every packet has a `portnum`. 0 to 63 core, 64 to 127 registered third-party, 256 to 511 private (`PRIVATE_APP` = 256, `ATAK_FORWARDER` = 257), MAX 511. Registered ports include `SERIAL_APP` 64, `IP_TUNNEL_APP` 33, `LORAWAN_BRIDGE` 75, `RETICULUM_TUNNEL_APP` 76 (doc, https://raw.githubusercontent.com/meshtastic/protobufs/master/meshtastic/portnums.proto ). So a private port can carry arbitrary bytes up to 233, but a node's `CORE_PORTNUMS_ONLY` rebroadcast mode will drop non-standard ports (doc).
- M20. **Discovery and UX.** Nodes broadcast NodeInfo and position periodically (intervals scale with network size, doc). Region must be set before transmit (doc). Configuration is by phone app, CLI, web, or QR/URL for channels, with a "modem preset" that all nodes in a mesh must share. Ignore MQTT / OK to MQTT flags control gateway uplink (doc).

### MeshCore

- M21. **Roles.** Companion (client, does not repeat, connects to phone or PC app over BLE, USB or WiFi), Repeater (relays, managed by USB web config or remotely over LoRa), Room Server (BBS-style store of posts), Sensor (telemetry). The advert flags byte encodes type: 1 chat, 2 repeater, 3 room server, 4 sensor (doc, https://github.com/meshcore-dev/MeshCore and `docs/payloads.md`). Firmware is MIT-licensed C++ with PlatformIO, 3.9k stars, 3,603 commits at read time (doc). The marketing site says AES-128 end-to-end and that relays cannot read content (doc, https://meshcore.co.uk/, third party site, not the project).
- M22. **Routing model is flood-then-learn-a-path, closer to path-based than Meshtastic.** Only repeaters (and room servers with `repeat on`) retransmit. A message floods first. The destination returns a PATH packet listing the repeaters used, the sender stores it per contact, and later packets are `Direct` and carry that path so only listed repeaters retransmit. On failure the client retries, resets the path, and floods on the last retry (doc, `docs/faq.md` https://github.com/meshcore-dev/MeshCore/blob/main/docs/faq.md ). Group channels always flood. Repeaters limit flooding with `flood.max`. A third-party wiki claims direct routing uses about 95 to 98% less airtime than perpetual flooding (search, https://wiki.eastmesh.au/meshcore/routing/ , the project's own claim not seen).
- M23. **Packet format.** Header byte: 2 bits route type (0 transport flood, 1 flood, 2 direct, 3 transport direct), 4 bits payload type, 2 bits payload version. Optional 4 bytes of transport codes (a region scope code plus a reserved 16-bit value). One path-length byte (6 bits hop count 0 to 63, 2 bits hash size minus 1, so 1, 2 or 3 byte hashes). Path up to 64 bytes. `MAX_PACKET_PAYLOAD` = 184 bytes. Payload types: REQ, RESPONSE, TXT_MSG, ACK, ADVERT, GRP_TXT, GRP_DATA, ANON_REQ, PATH, TRACE, MULTIPART, CONTROL, RAW_CUSTOM (0x0F, "raw bytes with custom encryption") (doc, https://github.com/meshcore-dev/MeshCore/blob/main/docs/packet_format.md ). Max hops: 64 with 1-byte hashes, 32 with 2-byte, 21 with 3-byte (doc, FAQ). Repeater firmware 1.14+ forwards 2 and 3 byte paths, older firmware drops them (doc).
- M24. **Identity and addressing.** Node identity is an Ed25519 public key (32 bytes). On the wire v1 uses a 1-byte hash (first byte of the public key) for source and destination, plus a 2-byte MAC. A 1-byte address collides at roughly 256 nodes, which the design tolerates because the MAC and context disambiguate (inference, not stated in the docs). Channels: shared key, with a 1-byte channel hash (first byte of SHA-256 of the key) (doc, payloads.md). Contacts and channels can be shared as `meshcore://contact/add?...` and `meshcore://channel/add?name=...&secret=...` URIs (doc, FAQ).
- M25. **Encryption.** The docs read say only "2-byte cipher MAC" and "AES-128" at the product level. The cipher mode, key derivation (Ed25519 to X25519 or not) and MAC construction were not stated (gap). A V2 spec with "new encryption specs" and "path hashes" is on the roadmap (doc, README). Adverts are Ed25519-signed: public key 32 B, timestamp 4 B, signature 64 B, then app data (flags, optional lat/lon, name) (doc). Plain text messages carry no sender signature field beyond the MAC (a `txt_type` 0x02 "signed plain text" exists, doc).
- M26. **Discovery.** Clients advertise only when the user triggers it, zero-hop or flooded. Repeaters send a flood advert every 12 hours by default (`flood.advert.interval`). A node with a wrong clock may fail to appear in discovery lists (doc, FAQ). There is no automatic identity directory.
- M27. **Store-and-forward.** Only Room Servers store messages. A client logging in receives "the previously 32 unseen messages" (FAQ) while a third-party wiki says 16 (search), so the figure is unverified. Channel messages are missed if the receiver is out of range (doc). Default guest password is `hello` (doc). Room server sync internals were not found (gap).
- M28. **Duplicates and loops.** Duplicates are dropped via a `SimpleMeshTables` seen-packet table, and flood packets accumulate repeater hashes in the path field so a repeater can see itself (search, third-party, https://wiki.eastmesh.au/meshcore/routing/ , not read in the official source). Table size and eviction not found (gap). Loops are bounded by `flood.max` and the 64-hop firmware limit (doc).
- M29. **Application data.** There is no application port space. Candidates: `GRP_DATA` (group datagram, marked unverified in the format doc), `RAW_CUSTOM` (unencrypted framing by the app, own crypto), `MULTIPART` (sequence of packets, layout not described). Message text length is not stated (gap). With 184 bytes of payload and the 1+1+2 byte header plus 5 bytes of timestamp and flag in a text message, usable text is about 175 bytes (calculation from documented numbers, not a stated limit).
- M30. **Operator UX.** Companion app (phone) or standalone firmware. Repeaters configured through a browser flasher/config tool over USB, or by remote CLI over LoRa (`set repeat on`, `set flood.max`, `set advert.interval`) (doc). Region scoping uses transport codes (doc). Firmware versions must be kept in step, because old repeaters silently drop newer packet forms (doc).

## Comparison

| Relay role | Transport Node (opt in, always on advised) | ROUTER / ROUTER_LATE / REPEATER / CLIENT_BASE | Repeater (clients never repeat) |
| Store-and-forward role | LXMF propagation node (`lxmd -p`), peers sync | S&F module on PSRAM ESP32 server (replay history) | Room Server (last 16 or 32 posts) |
| Routing | Path-based, next hop table learned from announces | Managed flooding, next-hop for DMs since 2.6 | Flood once, then Direct with stored path |
| Address | 128-bit hash of name + identity key | 32-bit node number | 1-byte key hash on wire (v1), 32-byte Ed25519 key in adverts |
| Identity key | Ed25519 + X25519 (512 bits) | X25519 (PKC), TOFU | Ed25519 |

## Implications for the sync contract

Numbers below are estimates from the documented limits, not measurements.

- I1. **Change records must have a compact binary encoding.** A 233 byte (Meshtastic) or 184 byte (MeshCore) payload, minus protocol framing, leaves roughly 170 to 230 bytes. The JSON record in [[research-sync-standardization]] (device, seq, hlc, collection, key, field, op, value, schema_version, tx) with a 36 character UUID is 150 to 250 bytes before the value. Needed: a CBOR or msgpack form with integer field numbers, a 16-byte (binary UUID) key, a numeric collection and field id from a schema dictionary, an HLC as 8 bytes, and device as a short index. Target a typical single-field change at about 40 to 60 bytes, so 3 to 4 fit in one LoRa packet. Reticulum (383 B) and LXMF (msgpack already) fit the same encoding. Reticulum and LXMF already use msgpack, so msgpack is the lowest-friction choice there, CBOR is the lowest-friction in other stacks. One of the two must be picked.
- I2. **A batch is the transport unit, a change is the data unit.** A "bundle" = header (sender device, range of seq, count) + list of changes, optionally compressed. Bundles above the radio MTU are chunked: `bundle_id, index, total, data`. Chunk loss on flooding meshes is common (Meshtastic reliable broadcasts get at most 3 sends, M18), so the receiver needs a selective retransmit request ("missing chunks of bundle X") or an erasure-style redundancy. Over Reticulum, a Link plus Resource already does chunking, ordering, integrity and retransmit (M8), so on that stack the contract needs no chunker of its own.
- I3. **Signing and encryption must be end to end, independent of the carrier, so relays can be untrusted.** Meshtastic channel packets are unsigned and decryptable by anyone with the key (M15). MeshCore messages carry a 2-byte MAC (M25). Neither authenticates a sender to a third party. So the contract must define its own envelope: authenticated encryption under a key shared by the owner's enrolled devices (one owner means one symmetric "vault key", or per-device pairwise keys), with the device id and bundle range authenticated as associated data. A relay then sees only an opaque blob plus routing metadata. Cost: a 64-byte Ed25519 signature is a third of a MeshCore packet, so sign (or MAC) per bundle, not per change. A 16-byte AEAD tag per bundle is cheaper than a signature when all peers share the key. Choose per Q-below.
- I4. **Identity should be a key.** Reticulum (M3) and MeshCore (M24) both use Ed25519 public keys as identity, and an address derived by hashing the key. Our device id should be the hash of the device's public key (16 bytes as Reticulum, or a truncation), not a counter. Enrollment becomes "exchange public keys (QR)", which is the same UX as MeshCore contact URIs and Meshtastic channel URLs (M20, M24). A short on-wire alias (1 to 4 bytes) can index the full id after first contact, as MeshCore does, with a collision rule (M24).
- I5. **Change ids already suit duplicate suppression.** (device, seq) is unique and idempotent on replay (E13). It also gives a seen-set per device as a single high-water mark plus a small gap list, which is far cheaper than a hash table of packet ids. What the mesh layer needs on top is a bundle id, because floods deliver the same chunk many times and mesh packet ids are only 32 bits (M17). Rule: the application layer drops anything below the device's contiguous high-water mark and ignores repeats within gaps, so duplicates are harmless without any mesh-level cache.
- I6. **Store-and-forward is a relay role that stores bundles for devices that are offline, and it needs only ciphertext.** Both LXMF propagation nodes (M10) and our Pi relay hold opaque blobs addressed by destination and fetched later. Needed in the contract: (a) relay-stored object = (recipient or vault tag, bundle id, size, expiry, sealed bytes), (b) a relay "fetch since cursor" call, which is our existing pull (cursor opaque, [[research-sync-standardization]] Recommended item 7), (c) retention rules (expiry, size cap, per-sender quota), (d) anti-spam: LXMF's per-message proof-of-work stamp with operator-set cost (M10) is the only mesh precedent found. For a private owner-only relay, an enrolled-device list is enough and stamps are optional.
- I7. **Relay-assisted sync needs peer-to-peer gossip, not only client to server.** Today pull and push assume a single server. With relays, the shape becomes "exchange summaries, then send what the other lacks". The summary is the version vector (device -> contiguous seq) which is small (16 to 32 bytes per device) and bounded by the number of devices. Pull with a cursor can stay as the API for a relay, with the cursor defined as a version vector instead of a server offset, so any peer can be a relay without a global sequence. Compaction ("every enrolled device has passed it", Q9 in [[research-sync-standardization]]) is the same vector, so a relay can purge below the minimum.
- I8. **Partial replication and bandwidth budgets become first-class.** A radio link carries about 0.3 to 22 kbps (M16), 5 bps minimum on Reticulum (M5), under duty cycle limits of 10% or 2.5% (M16). The sync layer needs: a priority per change (for example a task completion above a bulk contact import), a per-link byte budget with the ability to stop and resume, a collection/field filter in the subscription (already in the contract, Contract needs, "Partial replication"), and a "metadata only" mode (id, hlc, field, op, a hash of value) with the value fetched on demand. Large values (notes, attachments) need to be referenced by hash and sent only over links that can afford them (Reticulum Resource, or IP).
- I9. **HLC encoding must be small and the drift rule must tolerate sleeping, clock-less radios.** MeshCore warns a wrong clock breaks node discovery (M26). Devices with no battery-backed clock cannot produce a trustworthy HLC. Need: fixed 8-byte HLC, a rule for a device that has never had time set (use a counter epoch and accept the first received HLC), and the existing max-drift rule from [[research-sync-standardization]] Y22.
- I10. **Transport must not be assumed reliable, ordered, or bidirectional.** Meshtastic gives at most 3 or 5 sends (M18), MeshCore channel messages are lost if out of range (M27), and Reticulum Channel is reliable but needs a Link (M8). So push cannot return "accepted_through" synchronously. Make acknowledgement a later message (an ack bundle with the version vector) and make push idempotent. This also matches B1 to B10 style adapters, since apply stays idempotent.
- I11. **Schema dictionary.** Integer collection and field ids need a stable mapping shared by all devices, and the mapping version must travel with bundles (extends `schema_version` from the Recommended minimum record). Unknown ids are parked, never dropped, as already decided.

### What we should NOT copy

- N1. **Unsigned shared-key channels (Meshtastic channel PSK).** Any key holder can forge any sender (M15). The default public key is a published secret. No forward secrecy.
- N2. **Plain flooding as the default delivery path for data bulk.** Flooding is fine for small announcements and adverts. For sync bundles over multi-hop radio it burns scarce airtime on every repeater (M22 shows MeshCore itself leaves flooding after path discovery). Prefer learned next hops, or a direct link to the nearest relay.
- N3. **1-byte addresses.** MeshCore v1 uses one byte (M24) and its own roadmap lists "path hashes" for V2 (M23, M25). Collisions are tolerable for chat, not for a database identity. Keep full-key identity and use short aliases only as a cache.
- N4. **Trust on first use of keys, silently (Meshtastic).** Enrollment should be explicit.
- N5. **Unauthenticated or low-cost relay storage.** An open store invites spam, which is why LXMF added stamps (M10). Do not run an open relay for sync.
- N6. **Implicit acks by overhearing (Meshtastic broadcast).** It only works on a shared radio medium. Our ack must be an application message.
- N7. **A default shared guest password (MeshCore room server `hello`).** Not for a store of personal data.
- N8. **Role sprawl.** Meshtastic has 11 roles and 6 rebroadcast modes (M12) and the docs deprecate and warn about several. One relay role ("always on, stores bundles for known devices") and one client role are enough.
- N9. **Router-as-default.** Both Reticulum (M1) and Meshtastic warn that too many routers degrade the mesh. A Pi relay should be opt in.
- N10. **Per-change signatures.** 64 bytes each (Ed25519) is too much for 40 byte changes (I3).

### Can we ride on any of them?

- R1. **Reticulum is the only one that can carry application data today.** A Link plus Resource gives reliable large transfer, Channel gives reliable typed messages up to the packet MDU, and Buffer gives a stream (M8). Reticulum also works over TCP and WiFi, not only LoRa, so the same sync can run in a home network and over radio (M5). A sync adapter would be: each device is a Destination (Single) with an app name such as `appname.sync`, the relay announces it, peers open a Link and run the pull/push calls as Channel messages or Resource blobs. This needs a Python or compatible Reticulum implementation. A Go port or Rust implementation is not verified (gap), so our Go program would need a sidecar (`rnsd` plus a local socket) or a Reticulum-compatible implementation I did not verify exists.
- R2. **LXMF can carry change bundles as opaque `fields` values, with propagation nodes as free store-and-forward.** The message already provides signature, encryption and message-id dedup, adding 111 bytes. Fit: low-rate asynchronous sync of bundles to offline devices. Limits: no attachment API is documented, the maximum message size accepted by propagation nodes is not published in what I read (gap), and propagation requires a stamp per message. Using a public propagation network for personal data is possible because content is encrypted, but we would expose metadata (destination hash, size, time) to strangers, so a private propagation node on the owner's Pi is the safer fit (design inference).
- R3. **Meshtastic can carry bundles on a private portnum (256+), but not well.** 233 bytes per packet, 0.3 to 22 kbps, duty-cycle limits, hop limit 3 to 7, at most 3 to 5 retransmits, no signed channel messages, and `CORE_PORTNUMS_ONLY` repeaters will drop a private port (M12, M16, M18, M19). The Store & Forward module replays text/position history for clients, not arbitrary app data, and its own proto marks it "Work in Progress" (M19). `RETICULUM_TUNNEL_APP` (76) exists, which suggests the realistic route is Reticulum running over a Meshtastic link (the proto registers the port; behavior of that tunnel was not read, gap).
- R4. **MeshCore can carry only small custom packets, with no documented app-level API.** `RAW_CUSTOM` (0x0F) gives raw bytes with the app's own crypto, 184 bytes per packet, no ports, and requires custom firmware or a companion that exposes it (M23, M29). A Room Server stores posts for latecomers (M27), but it is a chat store, not a record store. Not a practical carrier for sync without firmware work.

## Recommended

Not a decision. Ranked.

1. **Keep the sync contract transport-independent and add a "constrained link profile".** Do not bind it to any of the three. Add to the contract: a compact binary record (I1), a sealed bundle envelope (I3), a version-vector cursor (I7), chunking (I2), acks as messages (I10), and a schema dictionary (I11). The IP profile (JSON over HTTP, existing Recommended section) stays as the default for pibrain.
2. **Reticulum is the only realistic network to ride on, and it is a transport choice, not a requirement.** Treat "Reticulum Destination + Link + Resource" as one binding of pull/push, and LXMF propagation node as one binding of the relay store. Prototype before committing: one Python script sending a signed, sealed bundle between two nodes over a TCP interface and over an RNode, to measure real throughput and the propagation node limits (the gap list below).
3. **The relay is a role in our own contract, not a mesh feature.** Define it as: holds sealed bundles for enrolled devices, serves pull by version vector, purges below the minimum acknowledged vector, rejects non-enrolled senders. A Raspberry Pi running this over HTTP and optionally over Reticulum covers the stated use case. Borrow from MeshCore the one-role-for-relay simplicity (M21) and from Reticulum the always-on, opt-in transport advice (M1).
4. **Borrow these ideas:** Reticulum key-hash addressing and signed announces (M3, M6), LXMF's message-id as hash of content (M9) and per-message proof-of-work only if a relay is ever public (M10), MeshCore's flood-then-learn-path (M22) and its explicit contact/channel share URIs (M24), Meshtastic's roles-as-rebroadcast-policy only as a model for relay modes (M12).
5. **Do not build a radio-first sync until the IP version is stable.** The wire changes in item 1 (compact record, bundles, version vector) are cheap to add early and expensive to retrofit, so add them to the contract now, but build the radio binding later.

## Open questions for the owner

- Q1. Is radio (LoRa) a real target, or is "any device can relay over IP/Tailscale" the actual need? Radio changes the encoding, chunking and budget requirements (I1, I2, I8). IP-only needs only the relay role and version vector.
- Q2. One key per vault (all devices share a secret) or per-device keys with pairwise sealing? A shared key is cheap for bundles (I3) but one lost device means rotating the vault key.
- Q3. Do you accept a Python Reticulum sidecar, or must the stack stay pure Go? This decides whether Reticulum is a binding (R1) or only an inspiration.
- Q4. Should relays be allowed to be untrusted third parties (public propagation nodes), or only the owner's own devices? Third parties need metadata hiding, stamps and quotas (N5, I6).
- Q5. Is a version vector as the cursor acceptable (I7)? It replaces the server-assigned offset in the existing pull call and changes the cursor from an opaque server offset to a peer-computable value.
- Q6. What is the largest value that must sync over a constrained link (notes, attachments)? It sets whether metadata-only plus fetch-on-demand (I8) is needed.
- Q7. Is signed authorship per change needed (multi-user later), or is per-bundle sealing enough (I3, N10, Q4 in [[research-sync-standardization]])?
- Q8. Should the constrained profile ship in the first spec (cheap to design, costly to retrofit) or wait until the SQLite and HTTP version is stable (Recommended item 5)?
